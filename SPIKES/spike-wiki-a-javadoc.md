## Description

An investigation must be conducted to determine how to connect the wiki to Javadoc.

### 1. Why connect the Wiki to JavaDoc?

Centralizing the "Source of Truth." Consider this scenario: A new developer joins the project and reads a guide on the Wiki titled "How to Build a Video Game Engine." They then examine the code and find a class named `MovementProcessor`, but they are unsure whether this class strictly implements the rules outlined in the Wiki or if there are hidden nuances. The solution: By linking them, the Wiki provides a direct link to the `MovementProcessor` class (via Javadoc) so the developer can view the actual parameters, while the Javadoc includes a link back to the Wiki to explain the business context (e.g., why a specific commission is charged, applicable legal regulations, etc.).

In large-scale or highly regulated projects (such as those in finance, healthcare, or government), "traceability" is often a requirement. Linking the Wiki to the Javadoc makes it possible to demonstrate to auditors or software architects that every requirement documented in the Wiki is accurately and functionally reflected in the source code classes.

**Wiki:** A GitHub Wiki is a built-in section of a repository used to host detailed, collaborative project documentation; it serves as a place to store usage guides, design principles, and software architecture details.

**Javadoc:** Javadoc is a tool that generates API documentation in HTML format based on special documentation comments embedded within the source code.

### 2. Linking from the Wiki to Javadoc

- Host the Javadoc: You can upload the HTML files generated by Javadoc to a hosting service like GitHub Pages, GitLab Pages, or an internal project server.

- Use direct links: Javadoc generates a predictable folder structure based on packages. 
    - Link example: https://github.ioLink

- Link to specific methods: You can use the HTML ID to navigate directly to a method. 
    - Example: .../MiClase.html#miMetodo(java.lang.String)

To ensure the Javadoc does not become outdated, HTML generation should be automated via a workflow (e.g., GitHub Actions) that compiles the comments and deploys the static files to GitHub Pages upon every release or push to the main branch.

URL structure:
- Class: https://<user-or-org>.github.io/<repository>/<package>/<Class>.html
- Method: https://<user-or-org>.github.io/<repository>/<package>/<Class>.html#<method>(<parameter_types>)

### 4. Linking from Javadoc to the Wiki

You can include Markdown or HTML links within code comments so that developers can navigate to the Wiki while reading the Javadoc. 
- Use the `{@link}` tag or basic HTML:
Java

/**
* This class handles system authentication. 
* For more details on the security flow, consult the
* <a href="https://github.com">Security Wiki</a>. 
*
* @see {@link https://tuempresa.com Confluence Wiki}
*/
public class Autenticador { ... }

- To link to external URLs like the Wiki, use standard HTML or the `@see <a href="...">` tag:

Java

/**
* This class handles system authentication. 
* For more details on the security flow, consult the
* <a href="https://github.com/tu-org/tu-repo/wiki/Seguridad">Security Wiki</a>. 
*
* @see <a href="https://github.com/tu-org/tu-repo/wiki/Seguridad">Security Architecture on Wiki</a>
*/
public class Autenticador { ... }

### 5. Configure the plugins in the pom.xml file 

Add the plugin declarations within the `<build><plugins>` section of your project:
```xml
<build>
<plugins>
<!-- Plugin to generate Javadoc -->
<plugin>
<groupId>org.apache.maven.plugins</groupId>
<artifactId>maven-javadoc-plugin</artifactId>
<version>3.6.3</version>
<configuration>
<show>public</show>
<nohelp>true</nohelp>
</configuration>
</plugin>

    - To verify this step was successful, run `mvn validate` in your terminal to confirm that the `pom.xml` file structure contains no XML errors. 
<!-- Plugin to publish documentation to GitHub Pages -->
<plugin>
<groupId>org.apache.maven.plugins</groupId>
<artifactId>maven-scm-publish-plugin</artifactId>
<version>3.2.1</version>
<configuration>
<scmBranch>gh-pages</scmBranch>
<pubScmUrl>scm:git:https://github.com/your-username/your-repo.git</pubScmUrl>
<content>${project.build.directory}/site/apidocs</content>
</configuration>
</plugin>
</plugins>
</build>
```
    - Execute generation and publication: Command terminal. Run the combined command in the terminal from the project's root folder:
                        `mvn javadoc:javadoc scm-publish:publish-scm`. 
    - To verify this step was successful, check the terminal output and confirm it ends with the message `BUILD SUCCESS`. 
    - Validate the update on GitHub: Open the repository on GitHub, switch to the `gh-pages` branch, and check the file structure. To verify this step was successful, ensure the folder contains the `index.html` file and your code packages with a recent commit date.

### 6. Process to verify publication on GitHub

1. Verify Workflow execution:
    - Actions tab on GitHub: Go to your repository on GitHub and click the **Actions** tab.
    - Select the "Generate & Deploy Javadoc" workflow run.
    - Confirm that the workflow has completed successfully, indicated by a green checkmark icon.

2. Configure the GitHub Pages source:
    - Repository settings: Go to **Settings > Pages** in your repository menu.
    - In the **Build and deployment** section, select the `gh-pages` branch and the `/` (root) folder.
    - To verify success, check that the page displays the top banner showing the public URL assigned to your site.

3. Validate the public Javadoc URL:
    - Web browser: Open the web address generated by GitHub Pages in your browser (e.g., `https://your-username.github.io/your-repo/`).
    - To verify success, ensure the page loads the interactive HTML site displaying the package and method structure of your Java code.

## General abstraction

Wiki → Javadoc flow: Wiki articles link to classes and methods hosted on a static server, allowing developers and auditors to verify the exact implementation. 

Javadoc → Wiki flow: Source code contains hyperlinked references to the Wiki to provide business context and technical traceability without cluttering code comments.

## Objectives

 The primary objective is to generate bidirectional hyperlinks or integrate the content so that code documentation and user documentation remain synchronized.
